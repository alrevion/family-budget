## Решение пользователя по AC-6 / AC-7 — ЗАКРЫТО: Вариант A

AC-6 требует скрыть в том числе **авторство** траты. AC-7 требует показывать партнёру строку «Скрытая трата, раскроется <дата>». При **двух** пользователях эти требования несовместимы: если строка видна и её создали не вы — автор вычисляется мгновенно. Это не техническое ограничение, а выбор между двумя вашими же требованиями.

| | Вариант A (текущий выбор плана) | Вариант B |
|---|---|---|
| Партнёр видит строку | Да: «Скрытая трата, 340 000, 20 авг, раскроется 27 авг» | Нет, строки в ленте нет |
| Что фактически скрыто | Категория и комментарий | Категория, комментарий, авторство, дата, факт существования |
| Сумма в балансе | Учтена (AC-6) | Учтена (AC-6) |
| Отчёт партнёра | Псевдокатегория «Скрытое» с суммой | Псевдокатегория «Скрытое» с суммой |
| Цена | Авторство и дата раскрыты. Партнёр видит: «за 5 дней до моего дня рождения потрачено 340 000» | AC-7 снимается. Партнёр видит только, что месячный итог не сходится с видимыми тратами |

Оба варианта не дают полной скрытности: сумма обязана попасть в баланс по вашему же требованию AC-6, поэтому расхождение в итогах заметно в любом случае. Вариант B скрывает больше, но убирает фичу «вижу, что что-то готовится».

**Выбран Вариант A** (решение пользователя, 2026-08-24). AC-7 сохраняется в исходном виде; AC-6 в части «скрыто авторство» признан невыполнимым при двух пользователях и компенсируется обязательным предупреждением в UI (R3). R3 реализуется как описано, дополнительных изменений не требуется.

## RALPLAN-DR Summary

### Principles
1. **Данные не теряются молча.** Любая операция с деньгами либо явно записана, либо не произошла. Расхождение показывается, а не чинится автоматически.
2. **Баланс — производная, не хранимое поле.** Правка задним числом обязана давать корректный результат без пересчётных скриптов.
3. **Одна деплой-единица.** Бот, API и Mini App — один Worker. Ноль обслуживания.
4. **Скрытие частичное и честное.** Пользователь должен видеть точную границу защиты в момент создания скрытой траты, а не догадываться о ней.
5. **Успех измеряется удержанием, не точностью.** Между «точнее» и «на два тапа меньше» побеждает второе. Удержание должно быть **наблюдаемым**, иначе принцип декоративен.

### Decision Drivers (top 3)
1. **Корректность денег при правках задним числом** (AC-4).
2. **Стоимость обслуживания = 0** — VPS отвергнут пользователем в Round 6.
3. **Приватность скрытых трат** в пределах, разрешённых AC-6.

### Viable Options

**Option A — Derived balance: хранятся только транзакции и аллокации, все агрегаты считаются SQL-запросом.** Выбран.
- Pros: правки задним числом корректны by construction; отчёты за любой месяц бесплатны; минимум кода.
- Cons: агрегация на каждый запрос (нерелевантно на ~55k строк за 10 лет); **не даёт enforceable-инварианта «Свободно ≥ 0»**.

**Option B — Materialized balance.** Отклонён: правка задним числом требует пересчётной логики, любой баг рассинхронизирует баланс с транзакциями. Прямой конфликт с Driver 1.

**Option B′ — Единая append-only таблица `entries` вместо `transactions` + `goal_allocations`.** Отклонён по двум причинам, ни одна из которых не про количество мест чтения:
1. `category_id` и `goal_id` становятся nullable FK с дискриминатором по `kind` — целостность перестаёт держаться схемой и переезжает в код.
2. Пропадает возможность держать `NOT NULL` на `category_id` для транзакций — единственная защита от записи без категории уезжает из схемы в код.

*Два обоснования отказа, приведённые в прошлых ревизиях, сняты как несостоятельные и здесь не используются: «предикат в семи местах чтения» (опровергается приёмом R1 — одна вью положила бы предикат в одно место) и «раздельные CHECK нельзя выразить без триггера» (выражаются одним составным CHECK по `kind`). Решение отклонить B′ держится на пунктах 1–2 выше.*

**Option C — Два Worker'а (бот и API).** Отклонён: удваивает деплой без выгоды, нарушает Principle 3.

### Признанное ограничение Option A
Option A гарантирует «баланс = Σ транзакций» и **не** гарантирует «Свободно ≥ 0». AC-4 разрешает задним числом уменьшить доход, после чего вчерашняя законная аллокация становится необеспеченной. Write-time проверка это не удержит — множество будущих правок неограничено. Решение — не прятать, а показывать (R1).

## Requirements Summary
Двухпользовательский трекер совместных финансов в узбекских сумах. Ввод через Mini App кнопками, без парсинга текста. Баланс = доходы − расходы, делится на «Свободно» и «В целях». Скрытые траты с таймером раскрытия до полугода. Месячный отчёт из 5 блоков, графики в браузере. Cron 1-го числа. Никакого AI (v2).

## Architecture

### Deploy unit
Один Cloudflare Worker:
- `POST /tg/webhook` — Telegram webhook (проверка `X-Telegram-Bot-Api-Secret-Token`), **всегда отвечает 200**
- `GET /api/health` — единственный маршрут в обход `initData`-проверки, отдаёт `{"ok":true}`. Существует ради Verification 7: доказывает, что asset-роутер не проглотил `/api/*`
- `GET|POST|PATCH|DELETE /api/*` — JSON API для Mini App (валидация `initData`)
- статика Mini App — через Workers Static Assets, **не** через Hono-маршрут
- `scheduled()` — два расписания, см. «Cron»

**`wrangler.toml` — фрагмент** (`main`, `compatibility_date` и `[[d1_databases]]` с биндингом `DB` обязательны и опущены только для краткости; без биндинга D1 не пройдёт Verification 1):
```toml
[assets]
directory = "./dist"
binding = "ASSETS"
run_worker_first = ["/api/*", "/tg/webhook"]
# not_found_handling НЕ задаём: SPA-режим не нужен, экран отчёта
# адресуется query-параметром ?month=YYYY-MM, а не путём.
# С single-page-application запросы к /api/* и /tg/webhook отдавали бы
# index.html с кодом 200 — Telegram счёл бы доставку успешной, бот молча умер бы.

[triggers]
crons = ["0 5 1 * *", "0 5 * * *"]
```
В каталоге ассетов не должно быть папок `api` и `tg`.
**Проверить перед стартом:** поддерживает ли установленная версия wrangler массив в `run_worker_first` (не булев). Если нет — обновить wrangler; Verification 7 это ловит.

### Cron (два расписания)
- `0 5 1 * *` (= 10:00 Asia/Tashkent 1-го числа) — месячный отчёт обоим: ключевые числа прошлого месяца **в тексте сообщения** + кнопка на `?month=<прошлый месяц>`.
- `0 5 * * *` — ежедневная проверка удержания. Условие: `MAX(created_at) < todayInTashkent() − 3 дня` **И** `app_state.last_nag_on < todayInTashkent() − 3 дня`. При срабатывании — одно сообщение «3 дня без записей» обоим и обновление `last_nag_on`.
  - Метрика по **`created_at`, не `occurred_on`**: пользователь, вносящий сегодня трату задним числом за прошлую неделю, приложением воспользовался — `MAX(occurred_on)` не сдвинулся бы, и напоминание пришло бы в день использования.
  - Cooldown обязателен: без него отъезд на две недели даёт 11 одинаковых напоминаний, и единственная митигация риска №1 становится его причиной. Заглушить бота нельзя — это же канал доставки месячного отчёта (AC-18). Хранится в существующей `app_state`, новых таблиц не появляется.
- **Диспетчеризация:** `scheduled()` различает расписания по `controller.cron`. 1-го числа оба тика приходят в одну минуту — если сработали оба, месячный отчёт отправляется, напоминание пропускается.
- Обе рассылки: `sendMessage` каждому в отдельном `try`, падение доставки одному не отменяет второго; ошибка логируется, повтор не делается (следующий тик придёт сам).

### Часовой пояс
Единственная утилита `todayInTashkent(): string` на `Intl.DateTimeFormat('en-CA', {timeZone:'Asia/Tashkent'})` → `YYYY-MM-DD`. Используется везде, где встречается «сегодня»: дата по умолчанию при вводе, сравнение `hidden_until`, вычисление прошлого месяца в cron, проверка удержания. Без неё трата, введённая в 02:00 по Ташкенту 1 сентября, уедет в августовский отчёт (UTC+5), тихо испортив оба.

### D1 Schema
```sql
CREATE TABLE users (
  telegram_id INTEGER PRIMARY KEY,
  name        TEXT NOT NULL
);

CREATE TABLE categories (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        TEXT NOT NULL,
  applies_to  TEXT NOT NULL CHECK (applies_to IN ('expense','income','both')),
  is_custom   INTEGER NOT NULL DEFAULT 0,
  is_archived INTEGER NOT NULL DEFAULT 0
);
-- уникальность только среди живых: архивная «Прочее» не должна
-- навсегда блокировать создание новой «Прочее»
CREATE UNIQUE INDEX idx_cat_name_live ON categories(name, applies_to) WHERE is_archived = 0;
-- по (name, applies_to), не по name: расходные «Подарки» из AC-16 не должны
-- запрещать доходные «Подарки» (подарили деньги)

CREATE TABLE transactions (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  amount       INTEGER NOT NULL CHECK (amount > 0 AND amount <= 100000000000),
  kind         TEXT    NOT NULL CHECK (kind IN ('income','expense')),
  category_id  INTEGER NOT NULL REFERENCES categories(id),
  author_id    INTEGER NOT NULL REFERENCES users(telegram_id),
  occurred_on  TEXT    NOT NULL,                       -- 'YYYY-MM-DD'
  comment      TEXT,
  hidden_until TEXT,                                   -- NULL = не скрыта
  created_at   TEXT    NOT NULL
);
CREATE INDEX idx_tx_month ON transactions(occurred_on);

CREATE TABLE goals (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  name          TEXT    NOT NULL,
  target_amount INTEGER NOT NULL CHECK (target_amount > 0),
  is_archived   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE goal_allocations (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  goal_id    INTEGER NOT NULL REFERENCES goals(id),
  amount     INTEGER NOT NULL CHECK (amount != 0),  -- отрицательное = возврат
  author_id  INTEGER NOT NULL REFERENCES users(telegram_id),
  created_at TEXT    NOT NULL
);

CREATE TABLE app_state (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- onboarding_done=1 после ввода стартового остатка. Проверять флаг,
-- а не наличие транзакции: AC-4 разрешает её удалить.
```

**Сид категорий (шаг 2):** 10 категорий AC-16 с `applies_to='expense'`; «Стартовый остаток» и «Зарплата» с `applies_to='income'`. Форма ввода фильтрует список предикатом `applies_to IN (:kind, 'both')` — **именно так, иначе категории `'both'` исчезнут из обеих сеток**. Без фильтра «Стартовый остаток» окажется в сетке расходов, а «Продукты» в сетке доходов. Пользовательская категория получает `applies_to` из текущего положения переключателя в момент создания. Категория «Скрытое» **не** сидируется: это метка агрегата, а не строка.

**Конвенция запросов месяца:** только диапазон `occurred_on >= '2026-08-01' AND occurred_on < '2026-09-01'`. Никаких `strftime`/`substr` — иначе `idx_tx_month` не используется.

**Агрегация в отчётах — по `category_id`, никогда по `name`.** Частичный уникальный индекс разрешает архивную и живую категорию с одинаковым именем; агрегация по имени слепила бы их в один сектор. По той же причине сопоставление месяцев в AC-20 идёт по `category_id`: `renameCategory` не должен рвать сравнение с прошлым месяцем.

**Миграция применяется целиком.** `migrations/0001_init.sql` содержит схему, вью и сид. При падении посередине: `wrangler d1 execute <DB> --file migrations/drop.sql` и заново. Для greenfield этого достаточно, полноценный rollback не нужен.

### R1 — Единственный источник «Свободно»
```sql
CREATE VIEW v_balance AS
SELECT
  (SELECT COALESCE(SUM(CASE kind WHEN 'income' THEN amount ELSE -amount END),0)
     FROM transactions) AS total,
  (SELECT COALESCE(SUM(amount),0) FROM goal_allocations) AS in_goals,
  (SELECT COALESCE(SUM(CASE kind WHEN 'income' THEN amount ELSE -amount END),0)
     FROM transactions)
  - (SELECT COALESCE(SUM(amount),0) FROM goal_allocations) AS free;
```
Один и тот же `v_balance` обслуживает главный экран **и** guard аллокации. Двух похожих запросов в двух местах быть не должно.

**Аллокация — атомарный условный INSERT, не read-then-write:**
```sql
INSERT INTO goal_allocations (goal_id, amount, author_id, created_at)
SELECT :goal, :amt, :author, :now
WHERE :amt > 0
  AND (SELECT free FROM v_balance) >= :amt
  AND (SELECT is_archived FROM goals WHERE id = :goal) = 0;
```
**`:amt > 0` в WHERE обязателен, и дублируется валидацией на границе API.** Без него отрицательная сумма проходит guard тривиально (`free >= -50000000` всегда истинно), `SUM` по цели уходит в минус, и деньги появляются из ниоткуда в «Свободно». Проверено прогоном в SQLite.
`meta.changes === 0` → HTTP 409. Читать из ответа того же `.run()`, **не** отдельным `SELECT changes()`: в D1 это второй round-trip и другое соединение. Закрывает и TOCTOU при одновременной аллокации обоими супругами (D1 не даёт изоляции между двумя раздельными round-trip), и попытку положить деньги в архивную цель — иначе они ушли бы из «Свободно» в невидимый карман, ровно то, ради чего написан R2.

*Форму `INSERT ... SELECT ... WHERE` без `FROM` проверить первым же тестом AC-P6, а не на проде.*

**Возврат из цели (AC-15)** — `:amt` передаётся **положительным**, в таблицу пишется `-:amt`:
```sql
INSERT INTO goal_allocations (goal_id, amount, author_id, created_at)
SELECT :goal, -:amt, :author, :now
WHERE :amt > 0
  AND (SELECT COALESCE(SUM(amount),0) FROM goal_allocations WHERE goal_id = :goal) >= :amt;
```
Выписано целиком намеренно: формулировка «тем же приёмом» оставляла знак `:amt` на усмотрение исполнителя, а при отрицательном `:amt` проверка становится тождественно истинной и возврат молча превращается в пополнение.

**Ретроактивный разрыв не чинится автоматически.** Если после правки `free < 0` — главный экран показывает отрицательное «Свободно» красным: «Отложено больше, чем есть. Верните деньги из цели или поправьте доход». Если `total < 0` (например, удалён стартовый остаток) — тот же приём, текст «Расходы превышают доходы. Проверьте, не удалён ли стартовый остаток». Никакого молчаливого урезания — Principle 1.

### R2 — Архивация цели
`archiveGoal(id)` в одной транзакции `batch()`:
```sql
-- 1. компенсация только если есть что компенсировать
INSERT INTO goal_allocations (goal_id, amount, author_id, created_at)
SELECT :goal, -(SELECT SUM(amount) FROM goal_allocations WHERE goal_id = :goal),
       :author, :now
WHERE (SELECT COALESCE(SUM(amount),0) FROM goal_allocations WHERE goal_id = :goal) != 0;
-- 2. архивация
UPDATE goals SET is_archived = 1 WHERE id = :goal;
```
Условие в шаге 1 обязательно: для цели **без** аллокаций `SUM` вернёт NULL, а `COALESCE(...,0)` дал бы `amount = 0` и нарушение `CHECK (amount != 0)` → 500 на самом частом сценарии «создал цель, передумал». Деньги возвращаются в свободные явной записью, а не пересчётом. Без этого мягкая архивация оставила бы деньги висеть под невидимой целью, а жёсткий `DELETE` упал бы на FK (D1 обеспечивает FK по умолчанию).

### R3 — Модель приватности (Вариант A, утверждён пользователем)
Маскирование в SQL-проекции слоя запросов, не в Mini App:
```sql
SELECT id, amount, kind, occurred_on,
  CASE WHEN masked THEN NULL ELSE category_id END AS category_id,
  CASE WHEN masked THEN NULL ELSE comment     END AS comment,
  CASE WHEN masked THEN NULL ELSE author_id   END AS author_id,
  masked AS is_masked,
  CASE WHEN masked THEN hidden_until ELSE NULL END AS reveals_on
FROM (SELECT *, (hidden_until IS NOT NULL
                 AND hidden_until > :today
                 AND author_id != :viewer) AS masked FROM transactions) ...
```
**`:viewer` биндится как JS `number`.** (В rev.3 здесь стояло обоснование через `1234 != '1234'` — оно снято как неверное: у колонки `author_id` INTEGER affinity, и SQLite приводит текстовый операнд к числу, проверено прогоном. Биндинг числом остаётся правильным по типизации, но фантомного риска не существует.)

Пути, ОБЯЗАННЫЕ идти через ту же проекцию, иначе утечка:
- список транзакций месяца;
- **топ-5 крупнейших трат (AC-22)** — крупная скрытая трата почти наверняка туда попадёт;
- ответы `PATCH`/`DELETE /api/transactions/:id`;
- одиночная выборка `GET /api/transactions/:id`, если появится.

**Не-автор не может править и удалять запись, пока `hidden_until > today`** → 403. Иначе партнёр удаляет подарок или видит категорию в ответе на PATCH.

**`hidden_until` нельзя изменить через PATCH.** Отклоняется не наличие поля, а **изменение значения**: `if ('hidden_until' in body && body.hidden_until !== row.hidden_until) → 400`. Безусловный отказ на наличие поля положил бы любую правку автором своей же скрытой траты — типовая форма отправляет загруженный объект целиком. Поле задаётся только при создании: ретроактивно скрыть то, что партнёр уже видел, нельзя.

**Псевдокатегория «Скрытое» в агрегатах отчёта** для стороннего зрителя — чтобы круговая диаграмма сходилась к общей сумме.

**Текст предупреждения на экране создания скрытой траты (обязателен):**
> «Партнёр увидит сумму, дату и выбранный срок — но не категорию и не комментарий.»

Срок упомянут намеренно: разница `reveals_on − occurred_on` однозначно выдаёт выбранный вариант, и «полгода» читается как «крупный сюрприз».

### R4 — Валидация `initData`
Схема выведения ключа: секрет = `HMAC_SHA256(data = BOT_TOKEN, key = "WebAppData")`, затем этим секретом подписывается `data_check_string`. Порядок аргументов регулярно инвертируют — зафиксировано намеренно.

1. `data_check_string` = все поля кроме `hash`, отсортированные по ключу, `key=value` через `\n`. **`signature` ВХОДИТ в строку.**

   > **Исправлено в rev.5.** rev.2–rev.4 требовали исключать и `signature` — ошибка планировщика, унаследованная от рекомендации Architect и не пойманная ни одним из двух проходов Critic. Telegram исключает `signature` только при сторонней Ed25519-проверке; при проверке по `BOT_TOKEN` в строку входят все полученные поля кроме `hash`. С Bot API 8.0 Telegram кладёт `signature` в каждый initData, поэтому его исключение давало бы 401 на любом запросе и делало Mini App полностью неработоспособным. Дефект пойман тестом AC-P3 — ровно тем требованием «внешний вектор, а не сгенерированный тем же кодом», ради которого критерий и был написан. Подтверждено независимым прогоном против `@telegram-apps/init-data-node`.
2. Значения берутся **URL-декодированными** (`user` — это JSON-строка). Сборка из сырой encoded-строки — классический баг.
3. Сравнение — через `crypto.subtle.verify('HMAC', key, sigBytes, checkStringBytes)`, а не ручное сравнение строк: сравнение внутри и в константном времени.
4. Транспорт — заголовок `Authorization: tma <initData>`. Не query-параметр: персональные данные осядут в логах.
5. Whitelist читает `user.id` **из проверенного `initData`**, после успешной верификации хэша. `ALLOWED_IDS` — CSV целых чисел (`"111111111,222222222"`), парсится в `number[]`, сравнение числовое. Проверка whitelist предшествует любому обращению к D1.
6. `auth_date` не старше 24 часов **и не из будущего**. Долго открытая вкладка начнёт получать 401 → клиент показывает «Сессия устарела, откройте приложение заново» и вызывает `WebApp.close()`. **`location.reload()` здесь давал бы бесконечный цикл:** `initData` лежит во фрагменте URL, перезагрузка его сохраняет, `auth_date` остаётся тем же просроченным. Reload оставить только для сетевых 5xx.
7. После верификации и whitelist — `INSERT INTO users (telegram_id, name) VALUES (?,?) ON CONFLICT(telegram_id) DO UPDATE SET name = excluded.name` с именем из проверенного `initData.user.first_name`. Без upsert первый INSERT транзакции падает по FK (`users` нигде не сидируется); `INSERT OR IGNORE` не годится — имя никогда бы не обновилось.

### Три открытых вопроса из спецификации — решения
1. **Правка транзакции из закрытого месяца.** Отчёты считаются по запросу, правка задним числом автоматически меняет исторический отчёт — прямое следствие Option A. Заморозка отклонена: для двух человек «моя правка не отразилась» хуже, чем «цифра за июнь изменилась». Смягчение: cron-сообщение несёт ключевые числа в тексте — история Telegram и есть иммутабельный слепок. Снапшот отчёта в БД отклонён: пришлось бы хранить два варианта (для автора и не-автора скрытых трат).
2. **История правок.** В v1 нет. Оба пользователя доверенные; audit trail — отдельная таблица + UI + фильтрация приватности. Смягчение: `created_at` сохраняется, `author_id` при правке не меняется. Follow-up.
3. **Регистрация Telegram ID жены.** Whitelist в secret `ALLOWED_IDS` через `wrangler secret put` — применяется к задеплоенному Worker сразу, redeploy не нужен. Отклонены `/register` с кодом (лишний флоу ради одноразового действия) и открытая регистрация (нарушает AC-25).

### Правка `kind` (income ↔ expense) — разрешена с подтверждением
AC-4 не перечисляет `kind` среди редактируемых полей, но опечатка в переключателе расход/доход — самый лёгкий промах в форме, и без правки она неисправима иначе как удалением (с потерей `created_at` и авторства). Решение: `kind` изменяем, но в том же диалоге UI **обязан потребовать выбор новой категории** из списка, отфильтрованного по новому `kind` — иначе доход останется в категории «Продукты», а запись мигрирует между блоками отчёта с бессмысленной категорией (схема этого не ловит: связи `category_id` с `kind` нет). `updateTransaction` проверяет соответствие `applies_to` новому `kind` и при несовпадении возвращает 400. UI перед сохранением показывает «Это изменит баланс на 10 000 000 сум» с явным подтверждением. Переворот дохода 5 000 000 в расход меняет `total` вдвое от суммы — пользователь обязан это увидеть до, а не после.

## Implementation Steps

1. **Скелет.** `wrangler.toml` (см. выше), `package.json`, TypeScript strict, Hono. Секреты: `BOT_TOKEN`, `WEBHOOK_SECRET`, `ALLOWED_IDS`.
2. **Миграция.** `migrations/0001_init.sql`: схема + `v_balance` + сид категорий (с `applies_to`). Плюс `migrations/drop.sql` для повтора при сбое.
3. **Auth** (`src/auth.ts`). Полностью по R4. Webhook проверяет секретный заголовок отдельно и **всегда отвечает 200**: Telegram повторяет доставку на не-2xx, а повтор создал бы дубль.
4. **Утилиты** (`src/time.ts`, `src/money.ts`). `todayInTashkent()`, `addDays(ymd, n)`, `addMonths(ymd, n)` **с клампингом переполнения** (`2026-08-31 + 6м = 2027-02-28`, а не `2027-03-03`, как даёт наивный `setMonth`), `monthRange(ym) -> [from, toExclusive)`, форматирование `Intl.NumberFormat('ru-RU')` + «сум», без дробной части. Все суммы целые, `Number.isSafeInteger` на границе.
5. **Слой запросов** (`src/queries.ts`). Чистые функции над D1: `getBalance()` (через `v_balance`), `listTransactions(viewer, month)`, `listMonths()`, `createTransaction`, `updateTransaction`, `deleteTransaction`, `listCategories(kind)`, `createCategory`, `renameCategory`, `archiveCategory`, `listGoals` (архивные исключены), `createGoal`, `allocateToGoal`, `deallocateFromGoal`, `archiveGoal`, `monthlyReport(viewer, month)`, `lastEntryDate()`, `getAppState(key)`, `setAppState(key, value)` — последние две обслуживают `onboarding_done` и `last_nag_on`, и обязаны иметь маршруты в шаге 6, иначе онбординг не сможет прочитать свой флаг. Маскирование (R3) применяется здесь и только здесь.
6. **API** (`src/api.ts`). REST поверх слоя запросов + `GET /api/health`. Валидация на границе: `amount` — целое в `(0, 10^11]`, для аллокаций и возвратов дополнительно `> 0`; `kind` из перечисления; `occurred_on` — валидная дата не в будущем по Ташкенту. **Срок скрытия клиент передаёт вариантом** (`'1d' | '1w' | '1m' | '6m'`), дату `hidden_until` считает сервер тем же `addMonths`/`addDays` — иначе клиент, посчитавший «полгода» своим способом, разойдётся с серверной границей на день и получит 400 ровно на той опции, ради которой правка и вносилась. Валидация превращается в проверку перечисления. **Границу считать через `addMonths`, не через «183 дня»:** 1 марта → 1 сентября это 184 дня, и фиксированная опция «полгода» из AC-5 возвращала бы 400 примерно в трети месяцев года — ровно в момент самого эмоционально нагруженного действия в продукте. `renameCategory` при конфликте имени → 409, не сырая SQLite-ошибка. `PATCH`, меняющий `hidden_until`, → 400.
7. **Тесты денежной и приватной логики.** `vitest` + `@cloudflare/vitest-pool-workers`, AC-P1…AC-P15. Ставятся здесь, а не в конце: это гейт шагов 5–6, а не финальная формальность.
8. **Mini App — каркас** (`app/`). Подключение `https://telegram.org/js/telegram-web-app.js` — **единственный разрешённый внешний скрипт**, исключение из правила «без CDN» (правило относится к библиотеке графиков). `WebApp.ready()`, `WebApp.expand()`, глобальный обработчик 401 → сообщение + `WebApp.close()` (R4.6). Нижняя навигация: **Главная / Лента / Цели / Отчёт** — четыре вкладки, по числу экранов. В rev.3 их было три при четырёх экранах, и лента (единственный вход в правку и удаление, AC-4) оставалась недостижимой, а Verification 6 невыполнимой.
9. **Mini App — онбординг.** Если `app_state.onboarding_done` не выставлен, вместо главного экрана показывается экран «Сколько у вас сейчас денег» с той же числовой клавиатурой, что и в форме ввода. Сохраняет транзакцию категории «Стартовый остаток» и ставит флаг. **Онбординг живёт в Mini App, не в боте:** бот может принять сумму только текстом, а текстовый ввод сумм отвергнут спецификацией. Бот на `/start` показывает кнопку открытия Mini App.
10. **Mini App — главный экран.** «Свободно», «В целях», **число** «Потрачено в этом месяце» — тап по нему открывает вкладку «Лента» за текущий месяц, — кнопка «+». Форма: числовая клавиатура → сетка категорий, отфильтрованная по `applies_to` → сохранить. Переключатель расход/доход. Флаг «скрытая» + срок + предупреждение из R3.
11. **Mini App — лента и правка.** Список транзакций месяца, тап открывает правку и удаление с подтверждением. Правка `kind` требует отдельного подтверждения с указанием влияния на баланс. Замаскированные показываются как «Скрытая трата, раскроется <дата>» и на редактирование не открываются.
12. **Mini App — цели.** Прогресс-бары, создание, «Отложить в цель», возврат в свободные, архивация. 409 от сервера показывается человеческим текстом («Свободных денег недостаточно»), а не как ошибка.
13. **Mini App — отчёт.** `?month=YYYY-MM` плюс **переключатель месяца** (`←/→` и список из `listMonths()`) — без него AC-24 не выполняется и митигация «cron не сработал → отчёт доступен вручную» ссылается на несуществующий путь. Пять блоков:
    - AC-19 круговая — **только расходы**, иначе в первый месяц стартовый остаток съест 95% диаграммы;
    - AC-20 сравнение с прошлым месяцем — **только расходы**, сопоставление по `category_id`; при отсутствии категории в прошлом месяце показывать «новая», а не деление на ноль;
    - AC-21 динамика итогов по месяцам;
    - AC-22 топ-5 трат, замаскированные по R3;
    - AC-23 блок называется **«Сэкономлено за месяц»** = `доходы − расходы за месяц`. Это НЕ сумма `goal_allocations`: термин «отложено» занят кнопкой «Отложить в цель», коллизия снята переименованием.
    Библиотека графиков на усмотрение исполнителя, требование одно: бандл инлайнится, внешних CDN нет.
14. **Бот** (`src/bot.ts`). `/start` — кнопка открытия Mini App. Никакого свободного текстового ввода трат.
15. **Cron.** Оба расписания по разделу «Cron». Если `web_app`-кнопка в сообщении окажется недоступна — фолбэк на ссылку `t.me/<bot>/<app>?startapp=<month>`.

## Acceptance Criteria
AC-1…AC-26 наследуются целиком из `.omc/specs/deep-interview-family-budget-v1.md`. **AC-7 сохраняется в исходном виде. AC-6** в части «скрыто авторство» помечен как невыполнимый при двух пользователях (решение пользователя от 2026-08-24, Вариант A) и компенсируется обязательным предупреждением в UI из R3.

Критерии реализации:
- [ ] AC-P1: после правки суммы транзакции трёхмесячной давности `getBalance().total` равен `Σ(income) − Σ(expense)`, пересчитанной независимым запросом; отчёт за тот месяц отражает новое значение немедленно. *(Агрегат нигде не закеширован.)*
- [ ] AC-P2: запрос с `telegram_id` вне `ALLOWED_IDS` возвращает 403 до любого обращения к D1.
- [ ] AC-P3: подделанный `initData` отклоняется. Тест использует **зафиксированный внешний вектор**, посчитанный `@telegram-apps/init-data-node`, а не сгенерированный тем же кодом — иначе тест самоподтверждается и не поймает перепутанный порядок аргументов HMAC.
- [ ] AC-P4: `hidden_until` дальше `addMonths(today, 6)` отклоняется с 400; опция «полгода», созданная 1 марта, принимается.
- [ ] AC-P5: `Number.isSafeInteger` на границе API отвергает нецелые и небезопасные суммы; `amount` в БД всегда INTEGER.
- [ ] AC-P6: аллокация при `free < amount` → 409 без создания записи; возврат больше отложенного по цели → 409; аллокация в архивную цель → 409; **аллокация или возврат с отрицательной или нулевой суммой → 400/409 без создания записи** (guard `:amt > 0` работает и на границе API, и в WHERE).
- [ ] AC-P7: после ретроактивной правки, делающей `free < 0`, API отдаёт отрицательное `free`, аллокации не изменены, главный экран показывает предупреждение. То же для `total < 0`.
- [ ] AC-P8: `archiveGoal` для цели **с** аллокациями возвращает деньги в свободные (`SUM` по цели становится 0); `archiveGoal` для цели **без** аллокаций возвращает 200 и не создаёт записей.
- [ ] AC-P9: ответ `/api/transactions` для не-автора скрытой траты не содержит `category_id`, `comment` и `author_id`, но содержит `amount`. То же для блока топ-5.
- [ ] AC-P10: `PATCH`/`DELETE` скрытой транзакции от не-автора → 403; `PATCH` с полем `hidden_until` → 400.
- [ ] AC-P11: транзакция, созданная в 02:00 Asia/Tashkent 1 сентября, попадает в сентябрьский отчёт. Тест гоняется в workerd (`@cloudflare/vitest-pool-workers`), не в node — иначе не проверяет наличие полного ICU.
- [ ] AC-P12 (закрывает AC-9): автор скрытой траты получает `category_id`, `comment` и `author_id` непустыми.
- [ ] AC-P13 (закрывает AC-8): транзакция с `hidden_until = today` видна обоим полностью; с `hidden_until = today + 1` — замаскирована для не-автора.
- [ ] AC-P14: `monthRange('2027-01')` корректен на границе года — «прошлый месяц» для январского cron даёт декабрь предыдущего года.
- [ ] AC-P15: ежедневный cron молчит, если `last_nag_on` моложе 3 дней, и молчит, если запись внесена сегодня задним числом (`MAX(created_at)` сегодня, `MAX(occurred_on)` неделю назад).
- [ ] AC-P16: `addMonths('2026-08-31', 6)` даёт `2027-02-28`, а не `2027-03-03`.

## Risks and Mitigations
| Риск | Последствие | Митигация |
|------|-------------|-----------|
| Неверная валидация `initData` | Посторонний читает финансы семьи | R4 целиком; AC-P3 на внешнем векторе; `crypto.subtle.verify` |
| Маскирование сделано в UI | Подарок виден в сыром JSON | Маскирование в SQL-проекции (R3); AC-P9 |
| Утечка через топ-5 или PATCH-ответ | То же | R3 перечисляет все пути; AC-P9, AC-P10 |
| Пользователь верит, что скрытие полное | Обманутое ожидание, потеря доверия | Текст предупреждения в R3; раздел «Открытое решение» |
| `free < 0` / `total < 0` после правки | Экран показывает несуществующее состояние | AC-P7: показывать, не чинить (Principle 1) |
| Гонка аллокаций у двух супругов | Отложено больше, чем есть | Атомарный условный INSERT (R1) |
| Архивация цели без аллокаций | 500 на самом частом сценарии | Условная компенсация (R2); AC-P8 покрывает оба случая |
| Аллокация в архивную цель | Деньги уходят в невидимый карман | Проверка `is_archived = 0` в том же INSERT (R1) |
| `users` не сидирован | Первая транзакция падает по FK | Upsert в auth-слое (R4.7) |
| SPA-fallback в `wrangler.toml` | Webhook получает 200 с HTML, бот молча мёртв | `not_found_handling` не задавать; `run_worker_first`; Verification 7 через `/api/health` |
| UTC вместо Asia/Tashkent | Ночные траты уезжают в чужой месяц, тихо | `todayInTashkent()` везде; AC-P11 |
| Граница «полгода» = 183 дня | Опция из AC-5 отказывает в трети месяцев года | `addMonths(today, 6)`; AC-P4 |
| Суммы через float | Накопление ошибки | Целые числа, `CHECK`, AC-P5 |
| Webhook-ретрай Telegram | Дубль записи | Всегда 200; онбординг по флагу |
| Cron не сработал | Отчёт не пришёл | Отчёт доступен вручную через переключатель месяца (шаг 13, AC-24) |
| Потеря базы | Годы семейных финансов | D1 Time Travel (30 дней) — **проверить, что точка восстановления существует**, Verification 8. Экспорт данных вне v1 сознательно |
| **Заброшенность через 2 недели** | Продукт не выполнил задачу | Ежедневный cron: `MAX(occurred_on) < today − 3` → одно сообщение. Метрика из спецификации: за первые 30 дней нет пропусков длиннее 3 дней подряд |
| Отчёт выглядит по-разному у двоих | Совместный просмотр расходится на псевдокатегории «Скрытое» | Принято: скрытые траты редки и самораскрываются, расхождение живёт до `hidden_until` |

## Verification Steps
1. `npx wrangler d1 migrations apply <DATABASE_NAME> --local` — схема и `v_balance` применяются.
2. `npx vitest run` — AC-P1…AC-P16 зелёные.
3. Деньги: доход 5 000 000, трата 340 000 → баланс 4 660 000; отложить 1 000 000 → Свободно 3 660 000, В целях 1 000 000, общий баланс не изменился.
4. Разрыв: при балансе 4 660 000 отложить 4 000 000, затем задним числом уменьшить доход до 3 000 000 → Свободно −1 340 000, аллокация цела, предупреждение на экране.
5. Приватность: A создаёт скрытую трату на неделю → в `/api/transactions` для B поля `category_id`, `comment`, `author_id` равны `null`, `amount` присутствует; трата видна замаскированной и в топ-5; `PATCH` от B → 403. У A та же трата полная.
6. Правка истории: отредактировать трату прошлого месяца → отчёт прошлого месяца показывает новое значение.
7. `npx wrangler deploy` + `setWebhook` → `/start` открывает Mini App; `curl <origin>/api/health` возвращает `{"ok":true}`, а не `index.html`.
8. `npx wrangler d1 time-travel info <DATABASE_NAME>` — точка восстановления существует. **И один прогон `time-travel restore` на локальной копии** — процедура, которую никто не выполнит до дня, когда она понадобится, не является митигацией.
9. Навигация: с главного экрана достижимы Лента, Цели и Отчёт; тап по «Потрачено в этом месяце» открывает ленту; в отчёте переключатель открывает прошлый месяц без deep-link из бота.
10. Правка `kind`: перевернуть доход в расход → диалог требует выбрать категорию расхода и показывает влияние на баланс; сохранение с категорией дохода → 400.

## ADR

**Decision.** Derived balance (Option A) на Cloudflare Workers + D1 в одной деплой-единице, с двумя раздельными денежными таблицами и единственным SQL-вью `v_balance` как источником «Свободно».

**Drivers.** (1) Корректность денег при правках задним числом — AC-4. (2) Нулевая стоимость обслуживания. (3) Приватность скрытых трат в пределах AC-6.

**Alternatives considered.** Материализованный баланс (Option B) — отклонён по Driver 1. Единая таблица `entries` (Option B′) — отклонён из-за nullable-FK с дискриминатором и потери `NOT NULL` на `category_id`; два прежних обоснования («предикат в семи местах», «раздельные CHECK без триггера») сняты как несостоятельные. Два Worker'а (Option C) — отклонён по Driver 2. Снапшоты отчётов — отклонены: потребовали бы двух вариантов из-за маскирования; заменены ключевыми числами в тексте cron-сообщения.

**Why chosen.** Единственная модель, в которой AC-4 выполняется без пересчётной логики. Признанная слабость — отсутствие enforceable-инварианта «Свободно ≥ 0» — не скрыта, а закрыта явным показом отрицательного значения (Principle 1) плюс атомарным guard'ом на момент записи.

**Consequences.** Исторические отчёты мутируют при правках задним числом — принято сознательно, смягчено числами в тексте cron-сообщения. Каждый запрос главного экрана агрегирует всю таблицу — несущественно на данном объёме. Скрытие частичное; точная граница вынесена пользователю отдельным решением, а не переписана планом.

**Follow-ups (вне v1).** Audit trail правок. Экспорт данных. Заморозка исторических отчётов, если мутация начнёт мешать. Пересмотр приватности при появлении третьего пользователя.

## Non-Goals
Наследуются из спецификации. Дополнительно вне плана: audit trail правок, заморозка исторических отчётов, повторяющиеся платежи, экспорт данных (восстановление — через D1 Time Travel).
